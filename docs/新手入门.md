# 从零看懂 Hydro CF 训练插件

这份文档写给会一点 C++、但没做过网站或多人项目的大一学生。你不需要先学完 JavaScript、数据库和网站开发；下面会在用到概念时解释它，并指出对应的代码在哪里。

本文讲解当前目录中的 `hydro-cf-training` 插件。读完后，你应当能说清一次训练的数据怎样流动，找到负责某个功能的文件，并在没有完整网站的情况下运行一个计分小实验。

## 1. 这个项目到底帮谁做什么

设想教练想让一个班的学生练习一场过去的 Codeforces 比赛。如果全靠手工，教练需要问每个人是否做过这些题，整理名单，统计规定时间内的提交，计算成绩，再记录每个人的进步。

这个插件把这些工作连起来：教练选比赛、检查已知做题历史、发布训练；学生签到后去 Codeforces 做题；插件取回提交记录，生成训练榜单，并计算本站的训练 Rating。

先分清三个名字：

| 名字 | 在这件事里负责什么 |
| --- | --- |
| Codeforces，简称 CF | 学生实际提交代码的地方，负责评测代码，并提供公开比赛和提交记录 |
| Hydro | 承载训练页面的网站系统，提供登录、用户、权限、数据库连接等基础能力 |
| 本插件 | 安装到 Hydro 上，增加 CF 训练、历史检查、班级管理、榜单和训练积分功能 |

**插件**是依附于另一个程序运行的扩展。这里的主体程序是 Hydro；本目录并不是下载后双击就能打开的独立网站。

学生的代码在 CF 上被评测。本插件根据 CF 返回的结果计算训练成绩，不在这里编译、运行学生的 C++ 代码。

另一个容易混淆的词是 **Rating**，即表示水平的评分。这里有三种不同的数值：一道题的难度 Rating、账号的 CF 官方 Rating、插件记录的本地训练 Rating。本插件更新的是第三种，不会修改 CF 官方评分，也不会修改 Hydro 自带积分。它利用历史比赛数据做模拟估计，不能当作官方评分的精确复算。

## 2. 从一道编程题，走到一个网站项目

写编程题时，你通常处理的是：

```text
输入 → main 函数中的计算 → 输出 → 程序结束
```

网站则持续运行，等待很多人的操作。学生点击“绑定账号”，教练点击“发布”，另一个学生刷新榜单，都可能在相近时间发生。程序除了计算，还要判断谁有权限、把数据保存下来、等待外部网站回应，并处理失败。

先用下面这张图认识各部分。箭头表示请求和返回数据的方向：

```text
学生或教练的浏览器
    │ 点击按钮、填写表单
    ▼
Hydro 接收请求 → 插件入口 index.js
                    │ 检查身份、参数，调用对应功能
                    ▼
              lib/service.js 协调工作
                 ├── lib/core.js 等：按规则计算
                 ├── MongoDB：保存或读取训练数据
                 └── lib/cf.js ↔ Codeforces：获取公开数据
                    │
                    ▼
              返回允许当前用户查看的数据
                    │
                    ▼
              浏览器更新表格、状态和曲线
```

图中有几个开发者常用的词：

- **前端**：在浏览器里运行、与用户交互的部分，例如表单、按钮、榜单。本项目主要在 `templates/`。
- **后端**：在服务器上运行的部分，负责校验权限、保存数据和计算成绩。本项目包括 `index.js` 和 `lib/`。
- **服务器**：持续运行 Hydro、接收浏览器请求的计算机或运行环境；开发时也可以是自己的电脑。
- **数据库**：专门保存和查询数据的程序。这里使用 MongoDB；退出页面不会因此删除数据库中的训练记录。
- **API（接口）**：程序向另一个程序提出请求的约定。浏览器调用插件接口，插件也会调用 CF 接口；这是两层不同的通信。
- **HTTP 请求**：浏览器与服务器通信的一种方式。这里读取数据通常用 GET，提交修改通常用 POST。

例如浏览器可以向插件的 `/cf-training/api` 发送“绑定账号”请求。数据采用 **JSON** 格式，它用字段名组织信息，形状类似：

```json
{"action":"bind","handle":"ExampleStudent"}
```

这只是格式示例，`ExampleStudent` 是虚构账号。`action` 表示要做什么，`handle` 表示 CF 用户名。真实请求还携带登录信息和页面提供的校验信息，所以把这段文字贴进地址栏不能完成绑定。

## 3. 跟着一名学生参加一次训练

下面的“小林”是虚构人物，用来解释真实功能。

### 第一步：绑定账号，准备历史记录

小林登录 Hydro，在学生页面填写自己的 CF handle。handle 就是 CF 用户名，Hydro 里的用户编号则叫 **UID**。插件把这两个身份关联起来。

保存绑定不代表已经核实了账号归属。后台会检查 CF 账号是否存在，并同步公开提交和 rated 比赛记录；教练还需要确认这个账号确实属于小林。插件不要求 CF 密码。

**同步**就是把远端的数据取回来，保存到本地。第一次同步可能有很多记录，因此分多次获取，每次取一页。页面显示“排队中”或“同步中”时，表示这项工作还没有完成。

### 第二步：教练选班级、选比赛

教练先维护班级名单，再为选中的班级筛选比赛。历史检查要回答：这些学生是否已经提交过相关题目，参加过相关比赛，或者手动报告自己见过题目？

这里的“没有已知接触记录”有条件：历史必须同步完整且足够新。抓取失败或历史未完成只能说明“未知”，不能因为列表为空就推断“没做过”。即使公开记录完整，也不能自动发现只看过题解、从未提交的情况。

随后教练导入原比赛的参照榜。**参照榜**保存历史选手的比赛表现和相关评分信息，供本地训练 Rating 计算使用。

### 第三步：建草稿，核对后发布

**草稿**表示配置还可以调整。教练可以替换题目，替换题沿用原题位置的基础分。这里要区分“原来的 C 题位置”和“实际让学生做的题”：位置保留，实际题目可以不同。

发布会锁定题目和计分规则。发布前也会检查相关历史条件。过期草稿可以改到未来时间；不使用的草稿可以取消，取消后仍保留记录。

### 第四步：签到，在统一时间内提交

小林签到，开赛后在比赛页打开实际题目，用绑定账号向 CF 提交代码。赛前学生接口不会返回题目列表。

插件按 Hydro 设置的统一时间范围统计，包含开始时刻，不包含结束时刻。例如设定 14:00 开始、16:00 结束，恰好 16:00 的提交不计入本场。自己在 CF 开启 Virtual 不会改变插件的统计时间。

### 第五步：赛后同步，再结算

比赛结束后，教练点击“同步本场所有学生”。这是为了重新取回覆盖整场时间范围的提交结果，不能仅用一次普通的近期刷新替代。

**结算**是把经过检查的本场结果正式记入训练档案。教练先预览，确认当前成绩和资格，再确认此次结算。同步未完成、仍有待评测提交等情况会阻止正式结算。

计入 Rating 的比赛中，学生是否更新评分还取决于签到、接触记录、是否被设为仅练习等条件。符合资格的学生即使零解题，也会参与评分；零解题不等于缺席。

### 第六步：查看记录，必要时纠正

结算会保留当时的成绩快照。**快照**就是固定保存某一时刻的数据，之后远端判题改变不会悄悄改写这份已结算榜单。

发现错误时，教练可以撤销结算、修正并重新同步，再预览和结算。后续本地评分会按比赛结束时间重新计算，因此历史最高分也可能下降。

源码用以下状态描述一场训练：

| 状态值 | 中文含义 | 可以怎样继续 |
| --- | --- | --- |
| `draft` | 草稿 | 调整配置、改期、发布或取消 |
| `published` | 已发布 | 按时间经历赛前、赛中、赛后，条件满足后结算 |
| `settled` | 已结算 | 查看已保存结果；撤销后回到 `published` |
| `cancelled` | 已取消的草稿 | 保留记录，不能继续发布或结算 |

“赛中”“赛后”不是这里的额外状态值，而是根据起止时间判断。比赛结束也不会自动把 `published` 改成 `settled`。

## 4. 文件这么多，先读哪些

先认识三个文件格式：`.js` 和 `.cjs` 在本项目中都是 JavaScript 代码；`.html` 是网页模板；`.md` 是像本文这样的 Markdown 文档。

JavaScript 在这里运行于两个地方：浏览器执行页面交互代码，**Node.js** 则让 JavaScript 能在浏览器之外运行，例如执行后端逻辑和测试。它们语言相同，但可调用的环境能力不同。

| 文件或目录 | 负责什么 | 阅读时可以带着的问题 |
| --- | --- | --- |
| [package.json](../package.json) | 记录项目名称、版本、入口和运行要求 | 用什么环境运行？有哪些测试命令？ |
| [index.js](../index.js) | 连接 Hydro，注册页面和 API，检查请求权限 | 一个按钮的请求会交给谁？ |

| [lib/service.js](../lib/service.js) | 协调同步、存储、训练结果和结算 | 完成一个操作需要哪些步骤？ |
| [lib/cf.js](../lib/cf.js) | 请求 CF，处理等待、超时和重试 | CF 暂时不回应怎么办？ |

第一次读代码，可以从 `lib/core.js` 的 `parseProblem` 开始，再看 `scoreRun`，然后看对应测试。它们输入、输出比较明确，接近你已经熟悉的编程题。

等你能读懂一个计算函数，再沿着下面的请求路线看 `index.js` 和 `service.js`。一开始不用从头读完最大的文件，也不用先研究全部 Rating 公式。

## 5. 沿着“绑定账号”追一次代码

在编辑器中打开整个插件文件夹，用跨文件搜索查找下面的名称。不同编辑器快捷键不同，通常可以在菜单里找到“在文件中查找”。

1. 在 `templates/cf_training_app.html` 搜索 `ct-bind`。提交绑定表单时，代码调用 `api('bind', v, true)`。`v` 是表单中的数据，`true` 表示使用 POST 提交。
2. 在同一文件搜索 `async function api`。这个函数用 `fetch` 发出请求，把 `action` 和参数转换成 JSON；收到失败响应时，它会抛出错误，由页面显示提示。
3. 在 `index.js` 搜索 `async post()`，再找 `a.action === 'bind'`。后端从当前登录用户取得 `actor`，调用 `service.bind(domainId, actor, a.handle)`。
4. 在 `lib/service.js` 搜索 `async bind`。它校验用户名格式、检查是否已被别人绑定、保存关联，再调用 `queueSync` 安排同步。
5. 搜索 `queueSync` 和 `tick`。前者记录需要做的任务，后者在后台推进任务。页面再读取状态时，才能看到任务的进展。

这里的 `domainId` 表示 **Hydro 域**，可以先理解为网站内一个独立的组织空间。域内可以有多个班级。班级用于组织成员，域则是账号绑定、训练档案等数据的隔离边界；二者不是同一个概念。

留意第三步：后端使用登录身份，不相信浏览器自报“我是哪个 UID”。浏览器里的内容可以被用户修改，因此隐藏按钮只能改善界面，真正的权限检查必须在后端完成。

这条路线也展示了为什么函数要分开：页面代码处理交互，入口处理请求，服务组织操作，具体模块处理计算和存储规则。以后查问题时，可以先判断问题发生在哪一段。

## 6. 读代码时最需要补上的几个概念

### 对象、数组、模块和异步

JavaScript 对象可以先类比成 C++ 的结构体，用字段名取值；数组类似顺序容器。例如 `{ uid: 7, handle: 'ExampleStudent' }` 是一个对象，`account.handle` 读取其中的用户名，`[]` 是空数组。

`const c = require('./lib/core')` 表示载入另一个文件导出的功能，随后可以用 `c.scoreRun(...)` 调用。`module.exports` 列出提供给其他文件的功能。相对路径从使用 `require` 的文件位置解析。

数组的 `filter` 可以理解为筛选，`map` 可以理解为逐个转换。例如 `rows.filter(row => row.eligible)` 保留符合资格的行；`row => row.eligible` 是一个短函数，对每一行返回是否符合资格。

`async` / `await` 用来组织需要等待的操作。`await` 表示当前函数等到操作完成再继续，等待网络或数据库时，运行环境仍可以处理其他工作。但把耗时计算写进 `async` 函数，不会自动把计算搬到另一个线程。

### 数据库保存哪些东西

MongoDB 把一条有字段的数据称为“文档”，把同类文档放入“集合”。可以先类比为一条结构化记录和一组同类记录；数据库里的“文档”并不是 Markdown 文件。

本插件使用六个逻辑集合，实际名称可能受到 Hydro 的数据库前缀配置影响：

| 集合 | 保存的内容 |
| --- | --- |
| `cftrain_state` | 每个域的账号、班级、训练配置、结算事件等主要档案 |
| `cftrain_submission` | 同步回来的提交记录 |
| `cftrain_catalog` | CF 比赛和题目资料 |
| `cftrain_reference` | 导入时冻结的历史参照榜 |
| `cftrain_job` | 等待或正在执行的后台任务及进展 |
| `cftrain_lock` | 协调后台任务执行，避免多个执行者冲突 |

每个域的主要档案放在一个文档中，提交记录和参照榜单独保存。这样便于一起更新相关配置，但容量有上限：当前实现限制单域最多 200 场训练、每场最多 100 人，主要档案接近 12 MB 时会拒绝继续写入。

### 后台任务和缓存为什么存在

抓取多年提交可能很慢，所以请求先登记任务，再由后台逐步执行。浏览器不必一直等着同一个请求，用户可以稍后刷新状态。任务进展写入数据库后，程序重启仍有依据继续处理。

Rating 计算的慢则主要来自计算量。项目用 **worker（工作线程）** 执行这部分计算，并用 **缓存** 暂存可重复使用的计算结果。缓存像计算过的草稿：输入相同就复用；输入改变后，需要计算新结果。

这些评分缓存位于进程内，重启后会丢失，但可以根据数据库中的正式档案重建。页面显示“计算中”，意味着结果尚未就绪，不等于评分为零。

### 两个人同时修改，为什么要检查版本

假设两个教练都读到第 10 版班级名单。甲添加学生并保存为第 11 版；乙随后按旧名单保存，如果直接覆盖，就可能丢掉甲的修改。

`service.change` 使用 `revision` 这个版本号：只有数据库仍处于自己读到的版本，才允许写回。版本已经改变就重新读取并尝试；持续冲突时提示刷新。这是在应对**并发**，即多个操作的执行过程发生交错。

结算预览也需要类似保护。预览生成的 `token` 是“这次确认对应哪一份结果”的校验值；如果同步记录、资格或档案已经变化，旧预览不能继续确认，否则用户确认的内容和实际保存的内容可能不一致。

另一个名为 CSRF token 的值用于校验页面发来的修改请求。两者虽然都叫 token，用途不同；前者关联结算结果，后者帮助防止其他网页借用用户登录状态发起修改。

## 7. 不装完整网站，也能亲手运行一段真实逻辑

这里先运行项目里独立的计分函数，不连接 Hydro、MongoDB 或 CF。示例里的学生、题目组合、时间和提交记录全部是**自造推演数据**，不代表真实比赛。

### 确认运行位置和 Node.js

用编辑器打开 `hydro-cf-training` 文件夹，并打开终端。**终端**是输入命令、查看程序输出的窗口。接下来的命令都在包含 `package.json`、`index.js`、`lib/` 的插件根目录执行。

```sh
node --version
```

项目声明要求 Node.js 22 或更高版本。如果提示找不到 `node`，说明运行环境尚未安装或终端找不到它；先完成 Node.js 环境准备，再继续。

这里的最小实验只用项目源码及 Node 自带能力，不需要先执行 `npm install`。`npm` 是 Node 配套的包管理和脚本执行工具，本实验还用不到它下载依赖。

### 创建并运行小实验

在插件根目录创建 `.test-output` 文件夹；如果已经存在，直接使用。在其中新建 `first-score.cjs`，填入以下代码。这个目录已被项目的 Git 忽略规则排除，适合存放本地实验输出。

```javascript

const member = { uid: 1, handle: 'ExampleStudent' };
const problem = { contestId: 1, index: 'A' };
const startAt = 1700000000000; // 本项目的训练开始时间使用毫秒
const run = {
  startAt,
  durationSeconds: 7200, // 两小时，时长使用秒
  slots: [{ index: 'A', actual: problem, points: 1000 }],
  rules: c.rules('CF'),
};

function submission(id, minutes, verdict) {
  return {
    id,
    creationTimeSeconds: startAt / 1000 + minutes * 60,
    problem,
    author: { members: [{ handle: member.handle }] },
    verdict,
  };
}

const submissions = [
  submission(1, 10, 'WRONG_ANSWER'), // 第 10 分钟答错
  submission(2, 30, 'OK'),           // 第 30 分钟通过
];

const result = c.scoreRun(run, submissions, member);
console.log('解题数:', result.solved);
console.log('本场得分:', result.points);
```

回到插件根目录的终端，执行：

```sh
node .test-output/first-score.cjs
```

预期输出：

```text
解题数: 1
本场得分: 830
```

计算过程是：基础分 1000，第 30 分钟通过，之前有一次有效错误提交。默认 CF 计分取 `1000 × (1 - 30 / 250) - 50 = 830` 与最低分 `1000 × 0.3 = 300` 中较大者。

注意：**830 是本场题目得分，不是 Rating**。Rating 还需要历史参照榜、学生原评分等输入。

可以只修改实验文件，观察三个变化：

| 怎样修改 | 预期结果 | 为什么 |
| --- | --- | --- |
| 把第一条的 `WRONG_ANSWER` 改成 `COMPILATION_ERROR` | 得分 880 | 编译错误不作为扣分的有效错误提交 |
| 把第二条的通过时间从 30 改成 120 | 解题数 0，得分 0 | 恰好结束时刻的提交不在统计范围内 |
| 保持原例，再追加第 40 分钟的 `WRONG_ANSWER`，使用新的提交 ID | 解题数 0，得分 0 | 当前 CF 计分实现以最后一次有效提交决定结果 |

每次只做一种修改，再恢复原例尝试下一种。ICPC 计分的规则不同：首次 AC 后停止累计该题；不能把两种赛制的结论混用。

## 8. 从运行函数到运行网站，还差什么

上面的函数不依赖登录和数据库，所以可以单独运行。完整插件的入口 `index.js` 则需要 Hydro 提供用户身份、权限、路由注册和数据库连接；直接执行 `node index.js` 不会启动一个可用训练网站。

**路由**是网址与处理代码之间的对应关系。Hydro 加载插件时调用它导出的 `apply(ctx)`，插件通过 `ctx.Route(...)` 注册页面和接口。安装成功后，用户才能在 Hydro 中访问 `/cf-training`。

目前 `package.json` 声明的宿主依赖范围是 Hydro `>=5.0.0 <6`。这是项目声明的范围，不表示每个版本都做过完整实测。当前版本是 `1.0.0-preview.2` 内部预览，具体已验证环境和剩余验收见 [README](../README.md)。

实际环境的安装、备份和恢复集中写在[部署与恢复](deployment-recovery.md)。其中：**部署**是把选定版本安装到目标运行环境；**备份**是保存可用于恢复的数据；**回退**是有问题时恢复到兼容的旧状态。页面导出的 JSON 不含全部提交与参照池，不能代替数据库备份。

已有独立测试环境时，再按[浏览器与完整候选验收说明](../test/e2e/README.md)验证真实页面流程。其中部分脚本依赖指定的 WSL、Docker 和容器配置，不能把文档中的环境名称直接当作自己电脑上已有的服务。

## 9. 第一次尝试修改项目，怎样知道改对了

先找一个能说清预期的小改动，例如改进一句按钮旁的说明。用页面文字搜索定位模板，修改后在测试环境查看实际显示。只调整文案时，不需要为了凑数量新写测试；若改了计分、资格或权限，则需要针对行为变化检查对应测试。

**Git**记录文件变化和版本。可以在插件根目录用下面两条命令查看当前目录的改动：

```sh
git status --short -- .
git diff -- .
```

第一条列出变化的文件，第二条展示已跟踪文件的具体差异。新建且尚未被 Git 跟踪的文件只会在第一条中出现，需要另行打开阅读。开始修改前就看一次，能分清哪些变化早已存在。

遇到问题时，先把现象定位到具体一步：

| 现象 | 先看哪里 |
| --- | --- |
| 命令提示找不到文件 | 终端是否在插件根目录，实验文件位置是否正确 |
| 本地计分与预期不一致 | 输入中的账号、实际题目、时间单位、赛制；对照 `test/core.test.js` |
| 请求返回 403 | 当前登录用户在当前域的权限；受托班级管理员不等于全域教练 |
| 页面一直显示同步失败 | 后台任务的目标、错误信息和更新时间，再检查对应 CF 请求 |
| 无法确认结算 | 页面列出的赛后扫描、待评测或预览变化原因 |
| 切换班级后显示了旧结果 | 前端请求返回顺序和当前选择是否仍匹配 |

向同学或维护者描述问题时，写出执行的命令或点击步骤、期望结果、实际结果和错误文字。这样别人才能复现，也能区分界面问题、计算问题和环境问题。

如果你已经能沿着“页面 → 接口 → 服务 → 数据/计算 → 页面”找到一项功能，并独立解释上面的 830 分从何而来，就可以开始读和修改一个小功能了。
