日期：2026-09-24。结论：**当前版本暂不建议作为正式 1.0 上线。** 已具备组赛、历史筛查、结算、多班级授权与学生统计的主要功能，但下列同步、计分和性能问题需要先修复；建议修复后先完成小班完整训练试运行。

审查对象为插件当前完整工作树，包含未提交的班级管理及其他修复。记录时 HEAD 为 `de8e7b5f298813697f258eeb69380e54915a23c3`，包版本仍为 `0.1.0`，因此 HEAD 本身不能代表本次受审代码。需求依据为插件 README、统计图实施方案、项目 CONTEXT 和 ADR 0002；未读取学生原始笔记。

本次只增加审查记录与忽略目录中的构造数据复现脚本，没有修改产品代码、版本号或既有工作树内容，没有安装候选插件、重启 Hydro 或修改真实学生数据。以下问题均仍待处理。

优先级：P1 为建议阻止正式发布的问题；P2 为需要在 1.0 前处理的功能问题。产品口径冲突另行明确，不应通过悄悄改文档掩盖。

## Standards

独立检查正确性、并发、运行成本和发布稳健性。未发现违反课程文件只读等适用仓库硬规则的变更；以下是实现缺陷，并非风格偏好。

### S1 · P1 · 打开页面会同步重算全域全部历史 Rating

- 位置：`lib/service.js:367`、`lib/service.js:370`；调用点 `index.js:68`、`lib/service.js:155`。
- 学生 dashboard 和班级榜每次请求均执行 `replay`，遍历全域有效结算，对每场每名学生重新运行参照评分引擎。即使访问者仅查看自己，后台仍计算全域历史；引擎缓存只缓存参照模型，没有缓存重算结果。
- 构造数据实测：Node v24.19.0，10 场 × 100 名学生 × 20,946 名参照选手，同一参照引擎已经缓存，`replay` 耗时 **21,089 ms**。期间预先安排的零延时定时器未得到执行，说明计算持续占用 Node 请求线程。该数字为本机合成负载结果，不是生产压测结论。
- 修复建议：以结算历史和初始评分的版本缓存派生结果，结算或撤销时失效；普通查看读取缓存。昂贵重算放到任务/worker 中，并避免多个请求重复计算。不要仅增加 HTTP 超时。
- 复验：多学生同时打开主页与班级榜，普通读取不重新运行全域评分；撤销、重新结算、补初始评分后结果仍一致。

### S2 · P1 · 旧同步请求能覆盖新发起的完整比赛窗口同步

- 位置：`lib/service.js:208`；关联 `index.js:250`、`lib/service.js:58`。
- 普通 `syncPage` 正等待 CF 返回时，教练点击“同步本场所有学生”，新完整窗口被写入 `account.cycle`。旧分页回来后无版本检查地覆盖 `cycle`；若旧分页已结束，则直接将新窗口清为 `null`。任务队列又会对同一账号正在运行的同步去重，新窗口没有独立后续任务保障。
- 纯内存复现：挂起 `user.status`，设置从十天前开始的新 cycle，然后让旧请求返回空页；最终 `done=true`、`status=ready`、`cycle=null`，新扫描丢失。
- 修复建议：为每轮扫描分配 generation/request ID；旧 generation 不得推进或结束新扫描。去重时保留更强的扫描范围请求，并确保后续任务执行。
- 复验：分页进行中触发全窗口刷新、重复刷新、任务重试/进程重启均不能缩短请求覆盖范围。

本轴共 2 项已复现缺陷，最高严重性 P1。`TrainingService` 同时负责队列、同步、筛查、统计和结算，是 possible Divergent Change；可后续按职责拆分，但不用为纯重构阻塞发布。

## Spec

### F1 · P1 · “赛后同步完成”不能证明已覆盖完整比赛窗口

- 位置：`lib/service.js:191`、`lib/service.js:356`。
- README 承诺：“赛后手动同步会覆盖完整比赛窗口，以处理重测。”`result.complete` 的注释也要求覆盖完整训练窗口。
- 实际上只要账号 `ready`、无排队任务、`lastSyncAt >= 比赛结束` 等条件成立，就允许结算；普通刷新只回看最近成功刷新前 24 小时，没有记录实际扫描窗口。延迟结算一周前的训练时，近期普通同步可以成功，旧比赛提交却未重新读取。
- 构造复现：旧赛本地保留一条 AC；普通同步取得 500 条近约 28 小时的提交后正常停止，未触及一周前的比赛；此时旧赛 `complete=true`，仍使用旧 AC 计分。如果该 AC 已被远端重测撤销，就会以旧结果结算。
- 修复建议：记录成功扫描的时间范围/代次，结算必须检查本场所需覆盖范围；覆盖不足时自动排队或明确要求本场同步。只检查刷新时间不够。
- 复验：延迟结算、早期 AC 重测、仅点个人同步、仅有例行增量刷新时均不能绕过本场覆盖要求。

### F2 · P2 · 删除自报记录会让发布时已知接触过的学生重新取得 Rating 资格

- 位置：`lib/service.js:351`、`lib/service.js:359`；关联 `index.js:167`、`index.js:243`。
- README 规定“已有接触记录……不更新 rating”，并强调删除手动标记“不改写已发布训练的历史检查快照”。
- 发布时 `run.screening` 保存接触证据，但结算资格只根据当前 `s.notices` 和公开提交重新计算，不使用已有快照。已在发布快照中列为接触过的学生，删除自己唯一的自报标记后，会从 `eligible=false` 变为 `true`；历史快照仍保留那条证据。
- 修复建议：默认保留发布时已有证据对本场资格的约束。若需要纠正误报，应由教练明确覆盖并审计；需明确发布到开赛之间新增自报记录如何影响本场。学生删除个人档案标记不应隐式撤销已发布比赛的资格依据。
- 复验：删除、更改、重加标记以及撤销后重结算；误报纠正有明确授权和记录。

### F3 · P2 · 学生比赛接口返回其他学生的接触检查详情

- 位置：`index.js:120`。
- 学生响应已剔除榜单行的 `history`，前端也只向教练展示“发布时的旧题检查”，但 `result.run = { ...result.run, ... }` 仍保留 `run.screening`。
- 构造 API 复现：以 UID 2 学生读取自己的比赛详情，可以从 JSON 的 `run.screening` 读到 UID 3 的 `touched`、`accepted`、`attended` 等筛查信息。不是页面显示问题，而是服务端响应字段边界不完整。
- 修复建议：学生比赛对象使用明确字段白名单，不直接展开内部 run。核对其他仅教练可见字段，同步保护已结算和未结算返回路径。
- 复验：检查原始 JSON，普通参赛者仍能看榜单和题目，但拿不到同学的历史检查细节。

### F4 · P2 · 选赛时切换班级，结果和翻页仍按旧班级查重

- 位置：`templates/cf_training_app.html:531`、`:538`、`:652`、`:655`。
- README：“筛选与创建始终使用所选班级当前名单。”
- 搜索提交时缓存 `discovery.groupId`，但切换参赛班级没有对应 change 处理；翻页继续读缓存，创建草稿却读当前下拉框。
- Edge 真实模板、构造 API 复现：选择 A 班搜索 → 切换 B 班 → 页面仍显示 A 的结果 → 下一页请求仍为 `groupId=A`。教练可能根据 A 班“无接触”的结果为 B 班组赛。
- 修复建议：切班即清空或重新筛选；为筛选请求设置序号，废弃旧班级的迟到响应，翻页参数与当前班级一致。
- 复验：A/B 快速切换、搜索和翻页乱序、班级名单更新后再次筛选。

### F5 · P2 · 过期草稿无法退出，会永久阻止成员换绑

- 位置：`lib/service.js:71`、`index.js:242`、`lib/service.js:405`。
- README 的换绑规则要求草稿或未结算比赛锁定账号；但系统没有取消、删除或修改草稿开赛时间的操作。
- 若教练创建草稿后未及时发布，超过开赛时间即不能发布，未发布又不能结算。该草稿仍永久匹配换绑锁，并占用 200 场容量。构造昨日草稿后尝试教练换绑已复现拒绝。
- 修复建议：增加带审计的“取消草稿”或“修改开赛时间”；换绑只检查有效、仍需保留账号身份的训练。已发布/已结算记录需要不同的取消或归档规则，不能直接套用删除草稿。
- 复验：过期草稿可退出，取消后换绑正常，其他有效训练仍保持锁定。

### F6 · P2 · “历史最高 Rating”与文档约定不一致，需确定产品口径

- 位置：`templates/cf_training_app.html:68`、`lib/service.js:370`；需求为 README：“历史最高 Rating（含起点，不随撤销结算丢失）”。
- 实现从当前有效 ledger 计算最高值，而 void 事件被排除。例如起点 1400，唯一一场涨到 1500，撤销后最高变回 1400。
- 建议优先明确语义：若显示“有效训练历史最高”，撤销错误结算后下降是合理行为，应据此更新文案与约定；若确需“曾展示过的最高值”，则应单独持久化，并说明它可能来自已撤销结果。不要仅为保持数值而混淆两个概念。

本轴共 6 项问题/不一致，最高严重性 P1；F6 需要产品口径决定。班级所有权、受限管理员、接收确认和旧转让请求失效机制未发现额外确定性缺陷。

## 功能建议

1. **同步诊断与结算就绪状态**：展示等待人数、进度、最近失败、可重试操作，以及本场提交窗口是否完整覆盖。直接减少教练判断“何时可以结算”的成本；覆盖校验属于 1.0 必修，完整诊断界面可分期实现。
2. **训练生命周期管理**：1.0 至少补草稿取消/改期；后续补训练归档、容量提示及审计查询。归档必须有可验证的恢复方式，不能只是导出后删除。
3. **教练班级报表**：按训练和时间段查看出勤、解题、Rating 变化并导出 CSV。区分“通过记录”和“独立掌握”；额外题目统计不应扩大班级管理员到全域访问。
4. **赛后复盘入口**：汇总本场未通过题、补题状态和学生复盘备注；不要求提交 CF 密码，也不把补题 AC 追加入已冻结结算。
5. **题目身份和接触补充**：维护不同比赛编号的共用题映射，支持教练确认误报、记录手工调整理由；这比在当前阶段加入复杂自动推荐更能改善陌生性判断。

建议将新报表、复盘和共用题映射安排为 1.1，先完成 1.0 的正确性、可恢复性与日常使用闭环。
