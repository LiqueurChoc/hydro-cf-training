# `test/core.test.js`：计分、资格与 CF 客户端的本地测试

对应源码：[test/core.test.js](../../../test/core.test.js)（对应实现：[lib/core.js](../../../lib/core.js)、[lib/cf.js](../../../lib/cf.js)）

## 准备了什么场景

全部使用**自造数据**（构造的提交记录、参照榜、假 `fetch`），不需要 Hydro、Mongo 或网络。

| 用例 | 场景 | 检查什么 |
| --- | --- | --- |
| 解析 | `2000/C`、`2000C`、题目链接；伪造域名链接 | 只接受 CF 公开标识，拒绝 `attacker.test` |
| 换题与窗口 | 原题提交、开赛前提交、窗口外提交混在一起 | 换题继承原位置基础分；只有实际题目、时间窗口内、本人提交参与计分 |
| CF 计分 | CE、先 AC 后 WA、先 WA 后 AC | CE 不扣分；最后一次有效提交决定结果 |
| 下限与去重 | 50 次失败 + AC、重复 AC、他人提交 | 得分不低于基础分 30%；去重；非本人提交不计 |
| ICPC | 首个 AC 后继续提交、罚时与并列排名 | 首 AC 后停止计分；罚时 = AC 用时 + 失败次数 × 10；同分按罚时排名 |
| 接触判断 | `unknown`/`clear`/`exposed`/`attended` 四种状态与 24 小时新鲜度 | 状态优先级与边界时间 |
| 评分算法 | 用一份"慢但直白"的独立实现 `oracle` 逐点对照 | 优化后的 `referenceEngine` 结果与直算完全一致（含并列与修正） |
| CF 客户端 | 并发发两个请求、第一次响应 `FAILED`；再调用未支持方法 | 真正串行（最大并发 1）、失败后重试、白名单外方法报错 |

## 为什么值得检查

- 计分规则是业务的核心承诺，边界特别多（CE、重交、窗口、换题），这些用例正是把规则写成可执行文档。
- 评分算法用"独立慢实现对照"的方式验证：防止为了加速而算错。改 [lib/core.js](../lib/core.js.md) 后必须让这组对照继续通过。
- CF 客户端用例证明"限速"不是注释而是行为。

## 怎样运行

```sh
cd <插件目录>
node --test test/core.test.js
```

不需要任何环境变量，不产生外部副作用。预期全绿（本次运行的总体结果见 [README.md](README.md)）。

## 容易误解的地方

- 这里的 `run`、`sub` 是测试内部构造的对象，字段可以比真实数据少；真实入口的字段以 [lib/service.js](../lib/service.js.md) 的调用为准。
- 用例里的数字是**解释规则用的**，不要当成生产阈值。
- 改计分规则时，先改这里的场景表达"新规则应该怎样"，再改实现——反过来做很容易把测试改成"实现当前行为"。
